# AINet-DB 校閲精度指標 定義書（2026-09-26 制定）

目的: モデル・パイプラインの世代交代による校閲精度の変化を、事後の文章読解（今回のような遡及的な手作業の抽出）に頼らず、機械可読な形で継続的に追跡できるようにする。指標は情報抽出（Information Extraction）タスクの標準的な評価法に準拠する（MUC/ACE系のスロット評価、Precision/Recall/F1、Slot Error Rate）。

このファイルは今後の全バッチで有効。次回以降のブリーフ（CHUNK_BRIEF・VERIFY_BRIEF）は本書を参照し、検証パス・自己裁定・Waka裁定の結果を下記の形式で `docs/model_accuracy_log.tsv`（バッチ単位）と `docs/model_accuracy_findings.tsv`（指摘単位）に追記する。

## 1. 評価単位: assertion（主張単位）

record（人物項目）単位ではなく、XML中の一つ一つの主張を評価単位とする:
- persName 1件、date 1件、relation 1本、placeName 1件、affiliation 1件、event 1件、bibl 1件、TMP/AIND/wd/gn の参照付与 1件、をそれぞれ1 assertion として数える。

情報抽出評価でいう「スロット」に相当する。record単位（正しいか誤りか二値）だと情報が粗すぎ、逆に文字単位だと細かすぎるため、この粒度を標準とする。

## 2. Gold standard（正解）の定義

Waka裁定を経て `Individuals/` に最終確定反映された状態を、その時点の gold とする。批判・改訂は今後も起こりうるので、gold は「その時点での best-known truth」であり絶対的真実ではない（この点は学術的にも明記して良い限界）。

## 3. 記録するイベント

検証パス・自己裁定・Waka裁定のいずれかの段階で、以下のいずれかが生じたら1行記録する:

- **誤りの発見**（重大度に関わらずすべて）
- **チェックして0件だった項目も分母のために記録する**（例:「毒wdの残存: 0/166」。Precision/Recallの分母がないと指標が計算できないため、「違反ゼロ」も情報として同じ重みで残す）

## 4. タクソノミー（固定語彙・変更しない）

### assertion_type
`persName` / `date` / `relation` / `placeName` / `affiliation` / `event` / `bibl` / `id_assignment`(TMP/AIND付与) / `wd_ref` / `gn_ref` / `other`

### error_category（標準IE評価の3区分）
- `FP`（fabrication）: 原文に根拠のない主張を追加した（誤って作り込んだ）
- `FN`（omission）: 存在すべき主張が欠落した（取りこぼし・見落とし）
- `substitution`: 主張自体は存在するが値が誤り（relation方向の誤り、日付換算の誤り、参照ID誤りなど）

この3区分から Precision・Recall・F1・Slot Error Rate をすべて機械的に算出できる。

### severity（既存の3段階を継続）
`H`（高確信） / `M`（中確信） / `L`（低確信・軽微）

### origin_stage / caught_stage（固定語彙）
`gemini_draft` / `claude_review`（チャンク校閲） / `verify_content`（内容検証） / `verify_mech`（機械検査） / `self_adjudication`（自己裁定） / `waka_final`（Waka最終裁定）

## 5. バッチ単位で必ず記録する分母

VERIFY_REPORT・ISSUES の冒頭に表形式で明記し、`docs/model_accuracy_log.tsv` に1行追記する:

| 列名 | 内容 |
|---|---|
| batch_id | 例: B94-98 |
| review_date | 校閲完了日 |
| pipeline_version | 下記§7のバージョンタグ |
| n_entries | 校閲件数 |
| draft_model | チャンク校閲を行ったモデル |
| verify_model | 検証パスを行ったモデル（内容・機械で別れる場合は`content=X;mech=Y`のように） |
| aggregator_model | 集約・自己裁定を行ったモデル |
| n_assertions_checked | 検証対象とした主張の総数（assertion_type別内訳があれば尚可） |
| n_assertions_correct | 正しかった主張数 |
| n_assertions_FP | 作り込み誤りの数 |
| n_assertions_FN | 取りこぼしの数 |
| n_assertions_substitution | 値誤りの数 |
| notes | 特記事項（一過性の論点による外れ値など） |

## 6. 算出指標（生データから事後計算・自動化可能）

- **Precision** = correct / (correct + FP + substitution)
- **Recall** = correct / (correct + FN + substitution)
- **F1** = 2PR / (P+R)
- **Slot Error Rate (SER)** = (FP + FN + substitution) / (correct + FN + substitution) — MUC系の標準指標。Recallの逆数に近いが、誤り全体を一つの比率で見たいときに使う
- **Record-level exact-match率** = 誤りゼロだった record 数 / n_entries — 直感的な「完璧だった項目の割合」

## 7. pipeline_version（QA体制のバージョンタグ）

工程（検証の段階数・チェック項目数）が変わるたびに明示的にバージョンを上げ、VERIFY_REPORTのヘッダーに明記する。既存バッチの遡及分類:

- `v1`: 単一検証パス、重大度分類なし（〜B59-63）
- `v2`: 単一検証パス、H/M/L分類あり（B64-67〜B79-83）
- `v3`: 内容検証＋機械検査の2パス体制（B86〜B89-93）
- `v4以降`: 今後、検証項目数や体制が変わるたびに追加しここに追記する

**この番号が変わるバッチをまたいだ比較は、検証の厳しさ自体が変わっているため単純比較しない**（既存レポート「校閲精度の推移」アーティファクトの限界と同じ注意）。

## 8. 記録先ファイル

- `docs/model_accuracy_log.tsv` — バッチ単位（§5の列）。1バッチ完了ごとに1行追記
- `docs/model_accuracy_findings.tsv` — 指摘単位。列: `batch_id, entry_id, assertion_type, error_category, severity, origin_stage, caught_stage, resolution, description`。検証・裁定で見つかった指摘1件につき1行追記

両ファイルとも今後永続的に追記していくログであり、書き換え・削除はしない（過去の全指標をいつでも再計算できるようにするため）。
